## 개념: 프로세스 상태

### Q1. 프로세스의 대표 상태와 의미
- **내 답변 요약**: 프로세스 상태가 무엇을 의미하는지 파악하지 못했다고 답했다.
- **평가**: 🔴 프로세스 생명주기와 스케줄링 관점의 상태 모델을 알지 못했다.

### Q1-tail. CPU 배정·실행·I/O 대기 상황의 상태
- **힌트**: CPU를 배정받기 전, 실행 중, I/O 완료를 기다리는 상황을 기준으로 상태를 구분하도록 유도했다.
- **내 답변 요약**: Idle 상태와 Waiting 상태라고 답했다.
- **평가**: Waiting은 맞았지만 Ready와 Running을 떠올리지 못했다. Idle은 일반적인 프로세스 생명주기 상태가 아니라 실행할 프로세스가 없을 때의 CPU 상태나 idle task를 가리킨다.

## 모범답안

- **New**: 프로세스가 생성되는 중인 상태
- **Ready**: 실행에 필요한 자원을 갖췄으며 CPU 할당만 기다리는 상태
- **Running**: CPU를 할당받아 명령을 실행 중인 상태
- **Waiting/Blocked**: I/O 완료나 이벤트 발생을 기다려 현재 실행할 수 없는 상태
- **Terminated**: 실행이 끝난 상태

`Ready → Running`은 스케줄러의 dispatch, `Running → Ready`는 타임 퀀텀 만료나 선점, `Running → Waiting`은 I/O 요청이나 이벤트 대기, `Waiting → Ready`는 I/O 또는 이벤트 완료로 발생한다. 일부 모델에는 메모리에서 내려간 Suspended 상태가 추가된다.

## 약점·복습포인트

- New·Ready·Running·Waiting/Blocked·Terminated 상태의 의미
- Ready는 CPU만 받으면 실행 가능하지만 Waiting은 사건 완료 전에는 실행할 수 없다는 차이
- 선점·dispatch·I/O 요청·I/O 완료에 따른 상태 전이
- Idle은 일반적인 프로세스 생명주기 상태가 아니라는 점

## 개념: fork·exec·Copy-on-Write

### Q1. fork와 exec의 정의·차이
- **내 답변 요약**: fork는 새 스레드를 생성하고 exec은 실행하는 것이라고 추측했다. PID·주소 공간과 셸의 실행 흐름을 이용한 힌트 후에도 프로세스 생성과 이미지 교체를 구분하지 못했다.
- **평가**: 🔴 핵심 약점. fork는 자식 프로세스를 만들고 exec은 현재 프로세스의 프로그램 이미지를 교체한다.

### Q2. Copy-on-Write 쓰기 폴트
- **내 답변 요약**: fork 시 전체 메모리를 즉시 복사하지 않고 부모의 물리 메모리를 읽기 전용으로 공유하며, 쓰기 시 폴트가 발생해 자신만의 메모리 영역을 만든다고 설명했다.
- **평가**: 🟢 정확. 사용자에게 전달되는 일반 오류가 아니라 커널이 처리하는 write-protection page fault라고 표현하면 더 정밀하다.

### Q3. 참조 카운트가 1인 COW 페이지
- **내 답변 요약**: 부모 종료 후 자식만 프레임을 참조해 참조 카운트가 1이면 일반 메모리와 다를 바 없으므로 반드시 복사할 필요가 없다고 설명했다.
- **평가**: 🟢 정확. 새 프레임 복사 대신 COW 표시를 제거하고 PTE를 writable로 바꿀 수 있다.

### Q4. fork 후 파일 디스크립터와 오프셋
- **내 답변 요약**: 부모와 자식이 파일의 다른 부분을 읽을 수 있어야 하므로 오프셋은 독립적일 것이라고 답했다. 파일 디스크립터 테이블과 open file description 관계를 제시한 힌트 후에도 회복하지 못했다.
- **평가**: 🔴 핵심 약점. 별도 FD 테이블의 엔트리가 같은 open file description을 가리키므로 현재 파일 오프셋을 공유한다.

## 모범답안

`fork()`는 현재 프로세스를 복제해 새 자식 프로세스를 만든다. 부모와 자식은 서로 다른 PID와 논리적으로 독립된 가상 주소 공간을 가진다. 호출 직후 같은 코드 위치에서 실행되며 부모에게는 자식 PID, 자식에게는 0이 반환된다.

`exec()`는 새 프로세스를 만들지 않고 현재 프로세스의 코드·데이터·힙·스택 등 프로그램 이미지를 새 실행 파일로 교체한다. PID는 유지되며 성공한 exec은 기존 코드로 돌아오지 않는다. 셸은 일반적으로 fork로 자식을 만든 뒤 자식에서 exec으로 새 명령을 실행한다.

fork 직후에는 부모와 자식의 PTE가 같은 물리 프레임을 쓰기 방지 상태로 가리킨다. 쓰기 시 write-protection page fault가 발생하면 커널이 COW 매핑인지 확인하고, 참조자가 여러 명이면 새 프레임을 할당·복사한 뒤 해당 프로세스 PTE를 writable로 갱신하고 명령을 재시작한다. 참조자가 하나뿐이면 복사 없이 기존 프레임의 COW 보호를 해제할 수 있다.

fork 후 부모와 자식은 별도의 파일 디스크립터 테이블을 갖지만 상속된 엔트리는 같은 커널 open file description을 가리킨다. 현재 파일 오프셋과 일부 상태 플래그는 이 객체에 있으므로 공유된다. 독립 접근이 필요하면 별도로 다시 open하거나 `pread`·`pwrite`처럼 명시적 오프셋을 사용한다.

## 약점·복습포인트

- fork는 자식 프로세스 생성, exec은 현재 프로세스 이미지 교체
- exec 성공 후 PID 유지와 기존 코드로 복귀하지 않는다는 점
- COW 쓰기는 커널이 처리하는 write-protection page fault
- 참조 카운트 1이면 복사 없이 PTE를 writable로 전환 가능
- 별도 FD 테이블과 공유 open file description 구분
- fork로 상속된 파일 디스크립터의 현재 파일 오프셋 공유

## 개념: 프로세스 간 통신(IPC)

### Q1. IPC의 정의와 필요성
- **내 답변 요약**: IPC는 프로세스 간 통신이며, 독립된 메모리 공간을 가진 프로세스끼리 데이터를 공유하기 위해 필요하다고 설명했다.
- **평가**: 정확. 프로세스 격리 때문에 직접 메모리에 접근할 수 없는 상황과 IPC의 필요성을 연결했다.

### Q2. 공유 메모리와 메시지 전달
- **내 답변 요약**: 공유 메모리는 같은 메모리 영역을 공유하고, 메시지 전달은 커널을 통해 데이터를 주고받는다고 설명했다. 메시지 전달은 커널 개입에 따른 오버헤드가 있고 공유 메모리는 일반적으로 빠르지만 동기화 문제가 발생한다고 답했다.
- **평가**: 핵심 trade-off를 정확히 설명했다. 공유 메모리도 생성·매핑과 페이지 폴트 등에는 커널이 관여하지만, 매핑 이후 일반 데이터 접근 경로에서 커널 개입과 복사가 적다는 표현이 더 정밀하다.

### Q3. 공유 메모리의 동시 수정
- **내 답변 요약**: race condition이 발생하며 뮤텍스와 세마포어로 동기화한다고 답했다.
- **평가**: 정확. 문제와 대표적인 해결 수단을 바로 연결했다.

### Q4. 프로세스 간 동기화 객체의 위치
- **내 답변 요약**: 처음에는 일반 뮤텍스를 각 프로세스가 따로 만들었을 때의 문제와 상태 저장 위치를 알지 못했다. 독립 주소 공간이라는 힌트 후 동기화 객체도 공유 메모리에 있어야 한다고 답했다.
- **평가**: 🟡 힌트 후 회복. 각 프로세스의 별도 뮤텍스는 서로 다른 객체이므로 상호 배제를 제공하지 않는다. 공유 메모리에 배치하고 process-shared로 설정한 뮤텍스나 양쪽이 동일하게 참조하는 이름 있는 세마포어가 필요하다.

### Q5. 로컬·원격 통신 수단 선택
- **내 답변 요약**: 같은 컴퓨터에서는 시스템 콜을 이용한 메시징이 가능하고, 소켓은 같은 컴퓨터와 서로 다른 컴퓨터 모두에서 사용할 수 있다고 설명했다.
- **평가**: 소켓의 적용 범위는 맞았지만 답변이 추상적이었다. 구체적인 로컬 IPC 수단과 주소 체계를 제시하지 못했다.

### Q6. 구체적인 로컬 IPC 수단
- **내 답변 요약**: 파이프·FIFO·메시지 큐·Unix domain socket 등의 구체적인 종류와 식별 방식을 답하지 못했다. 바이트 스트림·메시지 단위·통신 종단점이라는 힌트 후에도 회복하지 못했다.
- **평가**: 🔴 핵심 약점.

## 모범답안

- **익명 파이프**: 보통 부모·자식처럼 파일 디스크립터를 상속할 수 있는 프로세스 사이의 단방향 바이트 스트림
- **Named pipe/FIFO**: 파일시스템의 이름을 통해 서로 무관한 로컬 프로세스도 연결 가능한 바이트 스트림
- **메시지 큐**: 커널이 메시지 단위와 경계를 유지하며 버퍼링·전달
- **공유 메모리**: 같은 물리 메모리를 각 프로세스 주소 공간에 매핑. 데이터 전달은 빠르지만 별도 동기화 필요
- **Unix domain socket**: 파일 경로나 로컬 네임스페이스로 종단점을 식별하는 로컬 소켓
- **TCP/UDP socket**: IP 주소와 포트로 종단점을 식별하며 로컬 및 원격 통신 가능

각 프로세스가 독립적으로 생성한 뮤텍스는 서로 다른 객체다. 공유 메모리에 배치하고 process-shared 속성을 설정한 뮤텍스나 이름 있는 세마포어처럼 양쪽 프로세스가 동일한 동기화 상태를 관찰해야 공유 데이터를 보호할 수 있다.

## 약점·복습포인트

- 익명 파이프와 Named pipe/FIFO의 관계 유무·식별 방식 차이
- 메시지 큐가 메시지 경계를 유지한다는 특징
- Unix domain socket은 파일 경로나 로컬 네임스페이스, TCP/UDP socket은 IP·포트로 식별
- 각 프로세스가 별도로 만든 뮤텍스는 프로세스 간 동기화를 제공하지 않음
- process-shared mutex·이름 있는 세마포어 등 동일한 동기화 상태 공유

## 개념: Race Condition과 Critical Section

### Q1. Race Condition의 정의
- **내 답변 요약**: 둘 이상의 프로세스나 스레드가 동시에 한 자원에 접근해 실행 순서에 따라 결과가 달라지는 현상이라고 설명했다.
- **평가**: 핵심은 정확. 엄밀히는 공유된 가변 상태에 동시적으로 접근하고 하나 이상이 쓰기를 수행하며 적절한 동기화가 없을 때 발생한다.

### Q2. `count++`의 Lost Update
- **내 답변 요약**: A와 B가 모두 `count=0`을 각자 레지스터로 읽은 뒤 modify-write를 수행하면 둘 다 1을 써 최종값이 1이 된다고 설명했다.
- **평가**: 정확. `count++`가 read-modify-write로 분리된다는 점과 잘못된 interleaving을 설명했다.

### Q3. Critical Section의 정의
- **내 답변 요약**: Race condition이 발생할 수 있는 코드 영역이라고 설명했다.
- **평가**: 정확. 공유 자원에 접근해 한 번에 제한된 실행 단위만 진입해야 하는 영역이라는 표현을 더하면 완전하다.

### Q4. 올바른 임계구역 해결책의 세 조건
- **내 답변 요약**: 조건이 떠오르지 않았으며, 동시 진입·진입 결정 지연·특정 스레드의 무한 대기라는 힌트 후에도 용어를 답하지 못했다.
- **평가**: 🔴 핵심 약점. Mutual Exclusion·Progress·Bounded Waiting을 복습해야 한다.

### Q5. 인터럽트 비활성화를 이용한 보호
- **내 답변 요약**: 처음에는 답하지 못했지만 힌트 후 사용자 프로그램이 인터럽트를 비활성화하면 악의적 프로그램이 PC 동작을 멈추게 할 수 있고, 다른 코어의 실행 때문에 원자성이 보장되지 않는다고 설명했다.
- **평가**: 🟡 힌트 후 회복. 인터럽트 제어는 특권 연산이어야 하며, 한 코어의 인터럽트를 꺼도 다른 코어는 같은 공유 데이터에 접근할 수 있다.

### Q6. Spinlock의 동작과 trade-off
- **내 답변 요약**: 락을 기다리면서 CPU를 반납하지 않고 반복 확인하며, 짧은 대기에서는 컨텍스트 스위칭 비용을 아껴 유리하지만 대기가 길면 비효율적이라고 설명했다.
- **평가**: 정확.

### Q7. CAS를 이용한 상호 배제
- **내 답변 요약**: compare-and-swap 자체가 하드웨어적으로 원자적인 연산이라고 설명했다.
- **평가**: 부분적으로 정확. 여러 코어 중 하나만 `0→1` 변경에 성공하고 나머지는 실패하므로 상호 배제가 성립한다는 연결이 필요하다.

### Q8. Acquire·Release 메모리 순서
- **내 답변 요약**: 락 획득 이후 연산의 앞당김과 락 해제 이전 연산의 뒤늦춤을 막는 의미를 질문했으나 관련 용어를 들어본 적 없다고 답했다.
- **평가**: 🔴 L4 약점. 락 변수의 원자성과 임계구역 데이터의 순서·가시성 보장은 별개다.

## 모범답안

올바른 임계구역 해결책은 다음 조건을 만족해야 한다.

1. **Mutual Exclusion**: 한 실행 단위가 임계구역에 있으면 다른 실행 단위는 동시에 들어갈 수 없다.
2. **Progress**: 임계구역이 비어 있고 진입 요청자가 있으면 진입 결정이 무기한 미뤄져서는 안 된다.
3. **Bounded Waiting**: 진입 요청 이후 다른 실행 단위가 먼저 진입할 수 있는 횟수에 유한한 상한이 있어야 한다.

CAS 기반 spinlock에서는 여러 코어가 락 변수에 원자적인 `CAS(0, 1)`을 시도한다. 정확히 하나만 성공해 임계구역에 들어가고 나머지는 실패해 반복 대기한다. 짧은 임계구역에서는 문맥 교환을 피할 수 있지만 대기가 길면 CPU 시간을 낭비한다.

락 획득에는 **acquire semantics**, 락 해제에는 **release semantics**가 필요하다. Acquire는 이후의 메모리 연산이 획득 앞으로 재배치되는 것을 막고, release는 이전의 연산이 해제 뒤로 재배치되는 것을 막는다. Release와 acquire가 연결되면 앞선 임계구역의 쓰기가 다음 락 소유자에게 보이는 happens-before 관계가 만들어진다.

## 약점·복습포인트

- Mutual Exclusion·Progress·Bounded Waiting의 정의
- 사용자 프로그램의 인터럽트 비활성화가 위험한 이유와 멀티코어에서 부족한 이유
- CAS 원자성으로 정확히 한 실행 단위만 락 획득에 성공하는 과정
- 락 변수의 원자성과 보호 데이터의 메모리 순서·가시성 구분
- Acquire·Release semantics와 happens-before 관계

## 개념: Lock·Semaphore·Condition Variable

### Q1. Mutex의 정의와 동작
- **내 답변 요약**: 한 자원을 한 번에 하나의 작업에만 할당하며, 락을 획득한 작업이 해제하기 전에는 다른 작업이 획득할 수 없다고 설명했다.
- **평가**: 정확. 임계구역이 하나의 하드웨어 원자 명령이 되는 것이 아니라 참여자 사이에서 중간 상태가 관찰되지 않도록 상호 배제한다는 표현을 보강할 수 있다.

### Q2. Mutex와 Semaphore의 차이
- **내 답변 요약**: Semaphore에는 소유권이 없고 카운터를 이용해 여러 자원의 접근을 관리할 수 있다고 설명했다.
- **평가**: 정확. Mutex는 일반적으로 소유한 스레드가 해제하지만 Semaphore의 signal은 wait를 수행한 실행 단위와 달라도 된다.

### Q3. Counting Semaphore의 wait·signal
- **내 답변 요약**: wait는 카운터를 감소시키고 signal은 증가시킨다고 설명했다. 자원이 없으면 대기 상태로 들어가며 signal 후 큐에서 깨어난다고 보충했다.
- **평가**: 핵심 동작은 정확. 카운터 확인·갱신·대기열 진입 또는 깨우기가 원자적으로 연결되어야 한다.

### Q4. Semaphore 연산의 원자성
- **내 답변 요약**: 값이 1인 세마포어에서 두 스레드가 동시에 wait하면, 확인과 감소가 원자적이지 않을 경우 하나만 들어가야 하는 영역에 둘 다 들어갈 수 있다고 설명했다.
- **평가**: 정확.

### Q5. Condition Variable의 정의와 동작
- **내 답변 요약**: 개념이 떠오르지 않았으며, 락을 반납하고 잠들었다가 알림을 받고 조건을 재확인하는 방향의 힌트 후 인터럽트를 통해 동작할 것이라고 답했다.
- **평가**: 🔴 핵심 약점. Condition Variable은 일반적으로 하드웨어 인터럽트를 직접 사용하는 개념으로 설명하지 않는다.

## 모범답안

Mutex는 상호 배제를 위한 소유권 기반 락이다. 한 스레드가 획득하면 다른 스레드는 해제될 때까지 임계구역에 들어갈 수 없고, 일반적으로 소유한 스레드가 해제한다.

Counting semaphore는 사용 가능한 자원 수를 카운터로 표현한다. `wait(P)`는 자원이 있으면 카운터를 감소시키고 진행하며, 없으면 호출자를 대기시킨다. `signal(V)`은 대기자가 있으면 하나를 깨우고 그렇지 않으면 사용 가능한 자원 수를 증가시킨다. 검사·갱신·대기열 조작은 race condition을 막기 위해 원자적이어야 한다.

Condition Variable은 공유 상태가 특정 predicate를 만족할 때까지 스레드를 재우고, 상태를 변경한 스레드가 깨우기 위한 동기화 도구다. 자체적으로 공유 데이터를 보호하지 않으므로 Mutex와 함께 사용한다.

`wait(cv, mutex)`는 Mutex 해제와 대기 진입을 원자적으로 수행한다. 깨어난 스레드는 Mutex를 다시 획득한 뒤 반환한다. 상태 변경자는 Mutex로 공유 상태를 보호하면서 predicate를 변경한 후 `signal`로 하나를 깨우거나 `broadcast`로 모두를 깨운다. Spurious wakeup이나 다른 스레드의 선점 가능성이 있으므로 `if`가 아니라 `while`로 predicate를 재검사해야 한다.

```text
lock(mutex)
while (!predicate):
    wait(cv, mutex)
공유 상태 사용
unlock(mutex)
```

## 약점·복습포인트

- Mutex의 소유권과 Semaphore의 비소유권·카운터 의미
- Semaphore의 wait·signal에서 카운터와 대기열 조작이 원자적이어야 하는 이유
- Condition Variable은 상태 값이 아니라 조건 대기 큐이며 Mutex와 predicate가 실제 상태를 보호
- `wait`의 Mutex 해제와 수면 진입은 원자적이며, 깨어난 뒤 Mutex를 재획득
- Spurious wakeup과 선점 때문에 `while`로 predicate 재검사
- `signal` 자체는 조건 상태나 이벤트 이력을 저장하지 않음

- **평가**: 🔴 선행 지식 부족. 이전 파일 시스템 면접에서 확인된 디렉터리 엔트리·아이노드·데이터 블록 구조를 먼저 학습해야 한다.

## 모범답안

파일 하나를 생성하거나 수정해도 디스크에서는 디렉터리 엔트리, 아이노드, 데이터 블록, 빈 공간 비트맵 등 여러 위치가 변경될 수 있다. 갱신 도중 전원이 꺼지면 일부 쓰기만 영구 저장되어 구조가 서로 모순될 수 있다. 재부팅 후에도 파일 시스템이 유효하고 일관된 상태를 유지하도록 하는 문제가 Crash Consistency다.

예를 들어 블록 비트맵에는 사용 중이라고 표시했지만 어느 아이노드도 그 블록을 가리키지 않으면 공간이 누수된다. 반대로 아이노드는 블록을 가리키는데 비트맵에는 빈 블록으로 표시되면 다른 파일에 재할당되어 데이터가 손상될 수 있다.

Journaling은 실제 파일 시스템 위치를 수정하기 전에 수행할 변경을 로그에 먼저 기록하는 방식이다. 로그의 commit 기록까지 안전하게 저장된 작업은 장애 복구 시 재실행하고, 완료되지 않은 로그는 무시해 부분 갱신을 방지한다. 실제 학습에서는 write-ahead logging, transaction commit, checkpoint, metadata journaling과 data journaling의 차이를 추가로 익혀야 한다.

## 약점·복습포인트

- 디렉터리 엔트리·아이노드·데이터 블록·빈 공간 비트맵의 관계
- 여러 디스크 블록 갱신이 부분 반영될 때 발생하는 불일치
- Journaling의 log 기록 → commit → 실제 위치 반영 → recovery 흐름
- Metadata journaling과 full data journaling의 차이
- 별도 학습 후 재면접 필요
