## 개념: 트라이 (Trie)

### Q1. 정의
- **내 답변 요약**: 트리 자료구조의 일종으로 문자열 prefix 매칭을 효율적으로 탐색하기 위한 자료구조.
- **평가**: 정확.

### Q2. 노드 구성·연결
- **내 답변 요약**: 각 노드는 문자열의 캐릭터, 앞에서부터 부모-자식 관계로 연결.
- **평가**: 🟡 통용되는 단순화지만, 엄밀히는 각 노드가 자식 맵+end 마커를 갖는 구조.

### Q2-tail. 자식 저장 구조·단어 끝 표시
- **내 답변 요약**: 딕셔너리로 구현, end 마커로 단어 끝 판별(예: "car"/"card" 구분).
- **평가**: 정확.

### Q3. 복잡도·배열/해시셋 비교
- **내 답변 요약**: 삽입·탐색 O(L). 배열은 문자열 탐색에 부적절, 해시셋보다 공간 효율 좋음.
- **평가**: 🟡 모호함 — 후속 질문에서 스스로 정교화(공간 효율 주장은 정직하게 수정).

### Q4. 해시셋 대비 진짜 이점 (해시셋도 O(L)인데 왜 트라이인가)
- **내 답변 요약**: prefix 탐색 — 존재 유무, 개수 파악 가능(별도 처리 통해).
- **평가**: 정확. 핵심 차별점 정확히 짚음.

### Q5. 단어 수 카운트 구현
- **내 답변 요약**: 처음엔 세그먼트 트리식 재귀 갱신("range sum")으로 답변 → 챌린지 후 "삽입 시 바로 갱신 가능"이라는 더 간단한 방식으로 스스로 정정.
- **평가**: 자발적 자기수정 우수.

### Q6. 삭제 시 고려사항
- **내 답변 요약**: end 마커만 지우면 다른 단어가 안 쓰는 경로가 유령처럼 남아 잘못된 prefix 매칭 발생. 다른 문자열의 경로 사용 여부 추적 필요.
- **평가**: 정확.

### Q7. 공간 효율이 항상 참인가 (챌린지)
- **내 답변 요약**: 처음 비교 기준이 "모든 prefix를 해시셋에 저장하는 경우"였다는 것을 인지 → 단순 해시셋과 비교하면 트라이가 항상 유리하다고 생각하지 않는다고 정직하게 철회.
- **평가**: 정직한 수정.

### Q8. 트라이가 유리/불리한 조건
- **내 답변 요약**: prefix 중복 많으면 트라이 유리, 중복 없으면 노드 생성 오버헤드로 비효율.
- **평가**: 정확. 핵심 트레이드오프 정확히 짚음.

### Q9. 노드 오버헤드 완화 기법 (핵심 약점 → 힌트 후 회복)
- **내 답변 요약**: 처음엔 모름(동적 생성이라는 다른 개념 언급). 힌트("자식이 하나뿐인 체인을 압축할 수 있을까요") 후 "단일 자식 체인을 압축하고 필요시 다시 연장"이라는 핵심 아이디어를 스스로 재발견.
- **평가**: 🔴→🟢 힌트 후 회복.
- **모범답안**: 압축 트라이(Compressed Trie) / Radix Tree(Patricia Trie). 자식이 하나뿐인 노드 체인을 문자열 하나를 담은 간선 하나로 압축, 새 단어가 그 구간 중간에서 갈라지면 그 지점에서 노드를 분할(split). 노드 수가 문자 수가 아니라 분기점 수에 비례해 prefix 공유가 적어도 공간 효율적. IP 라우팅 테이블(최장 prefix 매칭)이 대표 실무 사례.

### 사용자 질문 — 해시셋에 모든 prefix 저장 시 문제점
- **질문**: 해시셋도 길이 L에 O(L)이면 문제없는 거 아닌가?
- **답변**: 프리픽스 "하나"의 삽입은 O(L)이지만, 길이 L인 단어 하나를 등록하려면 길이 1~L짜리 prefix를 전부 따로 만들어 넣어야 해서 총 비용이 O(1+2+...+L)=**O(L²)**. 트라이는 이미 존재하는 조상 노드를 재사용해 O(L)에 끝남 — 이 "공유의 유무"가 핵심 차이. 추가로 해시셋은 멤버십만 답하고, prefix 개수·열거는 트라이의 서브트리 순회로 자연히 해결되는 반면 해시셋은 별도 구조가 필요.

### 약점·복습포인트 (트라이)
- 압축 트라이(Compressed Trie/Radix Tree/Patricia Trie) 용어·구조 즉시 상기 안 됨(힌트 후 개념적 재발견)
- 단어 수 카운트는 삽입 경로상 노드마다 카운터 +1로 충분(세그먼트트리식 재귀 갱신 불필요)
- 해시셋에 모든 prefix 저장 시 O(L²)로 불어나는 이유(공유 부재) — 이번 세션에서 명확히 정리됨
