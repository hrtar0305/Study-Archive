# 네트워크 모의면접 — 포트와 소켓, SOP와 CORS

- 날짜: 2026-07-30
- 분야: 네트워크
- 유형: 모의면접
- 답변 방식: 타이핑
- 이해도: 🟡 보통

## 개념 마무리

포트 번호와 TCP 연결 식별, 리스닝 소켓과 연결 소켓의 차이는 대체로 이해하고 있었다. 힌트 이후 송신 측 multiplexing과 수신 측 demultiplexing의 방향도 바로잡았다. 다만 포트를 프로세스에 고정된 주소처럼 표현한 점, 소켓을 단순한 인터페이스로만 이해한 점, UDP의 `recvfrom`·`sendto` 처리 방식은 보완이 필요하다.

## 질문과 답변

### 1. 포트 번호와 소켓은 각각 무엇이며, IP 주소와 어떤 관계인가?

**답변**

> 포트 번호는 하나의 IP 주소 안에서 각 프로세스마다 통신 목적지를 구분하기 위해 부여한 세부 주소입니다. 소켓은 그러한 통신을 위한 인터페이스입니다.

**평가**

핵심 방향은 맞다. 다만 포트는 프로세스마다 영구적으로 하나씩 배정되는 값이 아니다. 하나의 프로세스가 여러 소켓과 포트를 사용할 수 있고, 운영체제의 정책과 옵션에 따라 포트를 공유하는 경우도 있다. 소켓은 단순한 함수 인터페이스보다 더 구체적으로, 운영체제 커널이 관리하는 통신 종단점 객체이며 애플리케이션은 파일 디스크립터나 핸들을 통해 접근한다.

### 2. 같은 서버 `10.0.0.1:8080`에 두 클라이언트가 접속하면 서버는 두 연결을 어떻게 구분하는가?

**답변**

> 출발지 IP와 포트가 다르기 때문입니다.

**평가**

정확하다. TCP 연결은 일반적으로 프로토콜, 출발지 IP·포트, 목적지 IP·포트의 조합으로 식별한다.

### 3. TCP 연결을 식별하는 값은 무엇이며 프로토콜도 식별값에 포함되는 이유는 무엇인가?

**답변**

> 순서는 정확하게 모르겠습니다. `(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트, 프로토콜 종류)`가 될 것 같습니다. 프로토콜 종류가 식별값에 포함되는 이유는 아마 서로 다른 프로토콜 방식으로 이루어지는 통신은 별개이기 때문일 것 같습니다.

**평가**

맞다. 이를 보통 5-tuple이라고 부른다. 방향을 고정해 쓰면 `(프로토콜, 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)`이며, TCP와 UDP는 별개의 전송 계층 프로토콜이므로 동일한 IP·포트 조합도 서로 다른 통신 종단점으로 취급된다.

### 4. 리스닝 소켓과 `accept()`가 반환한 소켓의 차이는 무엇인가?

**답변**

> listening socket은 서버가 클라이언트의 요청을 받아들이기 위해 open해 둔 정해진 번호이고, accept로 반환하는 소켓은 실제로 통신에 사용할 그 세션의 고유한 소켓이 됩니다.

**평가**

정확하다. 리스닝 소켓은 새 연결 요청을 계속 받으며, `accept()`가 반환한 연결 소켓은 특정 클라이언트와 실제 데이터를 주고받는다. 여러 연결 소켓이 같은 서버 IP·포트를 사용하더라도 상대 IP·포트가 달라 각각 구분된다.

### 5. Multiplexing과 demultiplexing은 무엇인가?

**첫 답변**

> multiplexing은 세션에서의 데이터 전송을 하나의 통로가 아닌 여러 통로를 통해 전송하는 것입니다. demultiplexing은 그러한 여러 통로로 전달된 데이터를 하나의 데이터로 합치는 과정이고요. 포트 번호와 소켓은 잘 모르겠습니다.

**힌트 후 답변**

> 그렇다면 multiplexing은 송신측, demultiplexing은 수신측에서 이루어지는 것이 될 것입니다. 그 과정에서 여러 프로세스에 대해 각각 목적지를 할당해야 하므로 포트 번호를 통해 프로세스를 특정하게 될 것입니다.

**평가**

힌트 뒤 핵심 방향을 바로잡았다. 전송 계층 multiplexing은 송신 측에서 여러 애플리케이션 소켓의 데이터를 받아 TCP·UDP 헤더를 붙여 하위 계층으로 보내는 과정이다. Demultiplexing은 수신 측에서 헤더의 프로토콜·IP·포트 등을 확인해 알맞은 소켓의 수신 버퍼로 전달하는 과정이다. 운영체제가 먼저 소켓을 찾고, 그 소켓을 가진 프로세스가 데이터를 읽는다는 순서를 기억해야 한다.

### 6. 클라이언트에도 포트가 필요한 이유와 임시 포트는 어떻게 정해지는가?

**답변**

> 왜냐하면 통신이 단방향으로 이루어지지 않기 때문입니다. 이 과정에서 애플리케이션이 직접 지정하지 않았다면 포트는 남는 포트 중 랜덤으로 배정될 것 같습니다.

**평가**

응답이 돌아올 종단점을 식별하고 여러 동시 통신을 구분해야 한다는 점에서 맞다. 애플리케이션이 직접 `bind()`하지 않으면 운영체제가 보통 ephemeral port 범위에서 정책에 따라 사용 가능한 포트를 선택한다. 단순히 전체 포트 중 완전 무작위로 고르는 것은 아니다.

### 7. 같은 호스트에서 TCP 53번과 UDP 53번 포트를 동시에 사용할 수 있는가?

**첫 답변**

> 가능할 것 같습니다. 왜냐하면 외부로 나가는 통신은 53번 포트를 공용으로 사용하지만 내부에서 각 프로세스마다 자신의 포트와 53번 포트 사이의 개별적인 통신이 있을 것이기 때문입니다.

**추가 질문 후 답변**

> 그렇다면 프로토콜 종류가 다르기 때문에 같은 객체로 인식하지 않기 때문이 될 것입니다.

**평가**

결론은 가능하며, 추가 답변의 이유가 정확하다. TCP 소켓과 UDP 소켓은 프로토콜이 다르므로 같은 로컬 IP와 포트 번호를 각각 바인딩할 수 있다. 처음 답변은 원격 목적지 포트와 로컬 바인딩 포트를 섞어 설명했다.

### 8. UDP 서버가 하나의 소켓으로 여러 클라이언트를 처리할 때 송신자를 어떻게 구분하며 어떤 API를 사용하는가?

**답변 흐름**

> 헤더를 통해 구분할 것 같습니다.

> 송신자를 구분하기 위해서는 IP 헤더의 출발지 IP값과 UDP 헤더의 포트 값으로 구분할 수 있습니다.

> 그 부분은 잘 모르겠습니다. `recvfrom`?

**평가**

출발지 IP와 UDP 출발지 포트로 송신자를 구분한다는 점과 `recvfrom()`을 떠올린 것은 맞다. UDP는 일반적으로 TCP처럼 클라이언트마다 `accept()`로 새 소켓을 만들지 않는다. 하나의 바인딩된 소켓에서 `recvfrom()`으로 데이터와 송신자 주소를 함께 받고, 그 주소를 대상으로 `sendto()`를 호출해 응답한다.

## 핵심 개념 정리

### 포트 번호

포트 번호는 TCP 또는 UDP 헤더에 들어가는 16비트 값이다. 한 호스트에 도착한 데이터를 어느 통신 종단점으로 전달할지 운영체제가 구분하는 데 사용된다. IP 주소가 네트워크상의 호스트를 찾는 데 쓰인다면 포트는 그 호스트 안의 통신 목적지를 세분화한다.

포트는 프로세스 자체에 영구적으로 붙는 식별자가 아니다. 한 프로세스가 여러 소켓과 포트를 사용할 수 있고, 하나의 서버 포트를 여러 연결 소켓이 함께 로컬 포트로 사용할 수도 있다.

### 소켓

소켓은 운영체제 커널이 관리하는 네트워크 통신 종단점 객체다. 애플리케이션은 파일 디스크립터나 핸들을 통해 이 객체에 접근하고 `send`, `recv` 등의 시스템 호출을 사용한다.

소켓에는 단순한 포트 번호보다 많은 정보가 연결된다.

- 전송 계층 프로토콜(TCP 또는 UDP)
- 로컬 IP 주소와 포트
- 필요한 경우 원격 IP 주소와 포트
- 송수신 버퍼와 각종 옵션
- TCP라면 연결 상태, 시퀀스·ACK 정보, 타이머, 흐름·혼잡 제어 상태

따라서 **포트 번호는 소켓을 식별하는 데 쓰이는 속성 중 하나이고, 소켓은 실제 통신 상태와 자원을 담는 커널 객체**다.

`IP 주소 + 포트 번호`는 보통 소켓 주소라고 부르며, 이것 역시 소켓 객체 그 자체는 아니다.

### 소켓의 생성과 사용

1. `socket()`으로 소켓 객체를 만든다. 이 시점에는 로컬 포트가 아직 없을 수 있다.
2. 서버는 `bind()`로 로컬 IP·포트를 지정하고 TCP라면 `listen()`으로 연결 요청을 기다린다.
3. TCP 서버의 `accept()`는 특정 클라이언트와 통신할 새로운 연결 소켓을 반환한다. 리스닝 소켓은 계속 남아 다른 연결을 받는다.
4. 클라이언트가 `connect()`할 때 로컬 포트를 지정하지 않았다면 운영체제가 보통 임시 포트를 선택한다.
5. 애플리케이션은 `send`·`recv` 또는 UDP의 `sendto`·`recvfrom`으로 데이터를 주고받고, 마지막에 소켓을 닫는다.

### 리스닝 소켓과 연결 소켓

서버의 리스닝 소켓은 예를 들어 `TCP, 10.0.0.1:8080`에서 새 연결을 받는다. 접속이 성립할 때마다 `accept()`가 별도의 연결 소켓을 만든다.

```text
리스닝 소켓: TCP, 10.0.0.1:8080

연결 소켓 A: TCP, 192.0.2.10:51000 -> 10.0.0.1:8080
연결 소켓 B: TCP, 192.0.2.11:52000 -> 10.0.0.1:8080
```

두 연결 소켓은 서버 측 IP와 포트가 같아도 클라이언트의 IP와 포트가 달라 서로 다른 연결이다.

### Multiplexing과 demultiplexing

- Multiplexing: 송신 측 전송 계층이 여러 소켓에서 나온 데이터를 모아 각 데이터에 TCP·UDP 헤더를 붙여 네트워크 계층으로 전달한다.
- Demultiplexing: 수신 측 전송 계층이 헤더의 프로토콜·IP·포트를 기준으로 데이터를 적절한 소켓의 수신 버퍼에 전달한다.

핵심 흐름은 `패킷 → 운영체제가 헤더로 소켓 식별 → 소켓 수신 버퍼 → 프로세스가 읽음`이다. 포트가 프로세스를 직접 가리키는 것이 아니라 소켓을 찾는 데 사용된다고 이해하는 편이 정확하다.

### TCP와 UDP의 소켓 처리 차이

- TCP 서버: 리스닝 소켓으로 연결 요청을 받고 `accept()`가 연결별 소켓을 만든다.
- UDP 서버: 연결 설정 없이 하나의 바인딩된 소켓으로 여러 송신자의 데이터그램을 받을 수 있다. `recvfrom()`이 데이터와 송신자 주소를 함께 반환하며 `sendto()`로 그 주소에 응답한다.
- UDP에도 `connect()`를 호출할 수 있지만 이는 TCP 핸드셰이크나 연결 소켓 생성을 뜻하지 않는다. 기본 상대 주소를 정하고 해당 상대의 데이터그램만 받도록 커널 동작을 제한하는 편의 기능에 가깝다.

## 모범 답안

> 포트 번호는 TCP·UDP 헤더의 16비트 값으로, 운영체제가 한 호스트에 들어온 데이터를 적절한 통신 종단점으로 역다중화할 때 사용하는 식별 정보입니다. 소켓은 운영체제가 관리하는 실제 통신 종단점 객체로, 프로토콜과 로컬·원격 주소, 송수신 버퍼, TCP 상태 등을 가집니다. 따라서 포트는 소켓의 속성 중 하나이며 프로세스 자체의 고정 식별자는 아닙니다. TCP 서버에서는 한 리스닝 소켓이 연결 요청을 받고 `accept()`가 연결마다 별도의 소켓을 반환합니다. UDP 서버는 보통 하나의 바인딩된 소켓에서 `recvfrom()`으로 데이터와 송신자 주소를 받고 `sendto()`로 응답합니다.

## 복습 포인트

- 포트는 프로세스의 고정 주소가 아니라 소켓을 찾는 데 쓰이는 헤더 값이다.
- 소켓은 API 이름만이 아니라 커널이 관리하는 상태와 버퍼를 가진 통신 객체다.
- Multiplexing은 송신 측에서 여러 소켓의 데이터를 모으고, demultiplexing은 수신 측에서 적절한 소켓으로 나눈다.
- TCP 연결은 프로토콜과 양 끝의 IP·포트로 구분한다.
- TCP 리스닝 소켓과 `accept()`가 반환하는 연결 소켓을 구분한다.
- UDP는 일반적으로 `accept()` 없이 `recvfrom()`·`sendto()`로 여러 송신자를 처리한다.
- TCP 53과 UDP 53은 프로토콜이 달라 동시에 바인딩할 수 있다.

# 개념 2 — 동일 출처 정책(SOP)과 CORS

- 답변 방식: 타이핑
- 이해도: 🟡 보통

## 개념 마무리

SOP가 교차 출처 요청 전송 전체를 차단하지 않고 주로 응답 읽기를 제한한다는 핵심과, CORS에서 서버가 허용 여부를 선언하고 브라우저가 집행한다는 구조는 이해했다. CSRF 상황에서 공격자 코드가 쿠키 값을 읽는 것이 아니라 브라우저가 조건에 따라 대상 서버의 쿠키를 자동 첨부한다는 점도 꼬리질문을 통해 정확히 설명했다.

다만 origin의 구성 요소를 처음에 IP와 포트로만 답해 scheme과 일반적인 host 개념이 빠졌고, 교차 출처 `<form>` 제출도 허용될 수 있다는 범위를 처음에는 놓쳤다. `Origin`, `Access-Control-Allow-Origin` 등 핵심 CORS 헤더와 preflight는 답하지 못했다. SOP를 서버 방어의 최종선을 클라이언트에 둔 것으로 이해하기보다, 브라우저 안에서 서로 신뢰할 수 없는 출처의 실행 문맥을 격리하는 플랫폼 보안 경계로 이해해야 한다.

## 질문과 답변

### 1. SOP와 origin은 무엇인가?

**답변**

> 웹 브라우저의 SOP는 동일한 origin에서 돌아온 요청만 자바스크립트 처리를 허용하는 것입니다. 이때 origin은 IP, port로 이루어집니다.

**추가 답변**

> 프로토콜 종류도 포함이 될 것 같습니다.

**평가**

SOP가 자바스크립트의 교차 출처 응답 접근을 제한한다는 방향은 맞았다. Origin은 정확히 `scheme + host + port`의 조합이다. Host는 IP 주소일 수도 있지만 일반적으로 도메인 이름도 포함하는 상위 개념이다. 셋 중 하나라도 다르면 다른 origin이다.

### 2. SOP는 교차 출처 요청 전송을 모두 막는가?

**답변**

> 모두 차단하지는 않습니다. img 등은 막지 않습니다. 이는 웹의 발전 과정에서 다른 사이트의 img를 임베딩하는 것이 빈번했기 때문에 이루어졌다고 알고 있습니다. 하지만 다른 것들은 막습니다.

**평가**

`<img>`와 같은 교차 출처 임베딩이 가능하다는 점은 맞았다. 다만 “나머지는 막는다”는 범위가 너무 넓다. `<form>` 제출과 일부 페이지 이동·리소스 임베딩 같은 교차 출처 요청은 전송될 수 있다. SOP는 요청 전송 전체보다 다른 출처의 응답이나 DOM을 자바스크립트가 읽는 것을 주로 제한한다.

### 3. 교차 출처 form 요청과 CSRF

**답변 흐름**

> SOP는 보내는 것을 막는 정책이 아니라고 알고 있습니다.

> 가능한 시나리오는 사용자가 공격자의 사이트에 접속하여 어떠한 버튼을 클릭하였을 때 해당 버튼에 작성된 스크립트가 사용자의 브라우저에 있는 쿠키를 첨부하여 은행 등의 사이트로 HTTP 요청을 보내는 것입니다. 이 요청이 사용자의 은행 잔고를 어딘가로 보내는 요청이었다면 공격이 성공하게 됩니다.

**평가**

CSRF 공격의 전체 흐름을 잘 설명했다. 처음에는 스크립트가 쿠키를 직접 첨부하는 듯 표현했지만, 추가 질문에서 공격자가 쿠키를 읽는 것이 아니라 브라우저가 대상 서버의 쿠키를 조건에 따라 자동 첨부한다고 정확히 정정했다. 공격자가 응답을 읽지 못해도 상태 변경이 실행되면 CSRF의 목적은 달성될 수 있다.

### 4. CORS는 무엇이며 누가 허용 여부를 결정하는가?

**답변**

> CORS는 SOP로 인해 발생하는 불편함을 해결하기 위한 정책입니다. 예를 들어 백엔드와 프론트가 서로 다른 서버에서 작동하고 있는 경우 백엔드에서 돌아온 응답을 프론트에서 SOP로 인해 처리하지 못하게 됩니다. 이를 CORS로 해결합니다. 서버 쪽에서 응답을 보낼 때 이 도메인에서는 응답을 처리해도 된다는 정보를 같이 보냅니다. 이를 브라우저가 확인하여서 그 목록에 포함되어 있다면 자바스크립트 처리를 진행합니다.

**평가**

핵심 구조가 정확하다. 서버가 허용할 origin을 응답으로 선언하고 브라우저가 그 선언을 검사해 교차 출처 응답을 자바스크립트에 공개할지 결정한다. CORS는 서버 측 인증·인가를 대신하는 보안 수단이 아니라 브라우저의 SOP에 선택적 예외를 부여하는 메커니즘이다.

### 5. CORS의 요청·응답 헤더

**답변**

> 헤더의 이름은 잘 모르겠습니다.

힌트로 두 헤더 모두 `Origin`을 포함하고 응답 헤더가 `Access-Control-Allow-...` 형태임을 제시했지만 기억하지 못했다.

**평가**

이번 개념의 명확한 약점이다. 브라우저는 요청에 `Origin`을 보내고, 서버는 응답의 `Access-Control-Allow-Origin`으로 허용 출처를 알린다.

## 추가 질의응답

### CSRF는 누가 방어하는가?

SOP는 공격자의 응답 읽기를 제한하지만 인증된 상태 변경 요청 전송을 항상 막지는 않으므로, CSRF는 기본적으로 서버가 방어해야 한다.

- 예측하기 어려운 CSRF 토큰을 요청 본문이나 헤더로 제출하고 서버가 검증
- `SameSite` 쿠키로 교차 사이트 요청의 쿠키 자동 첨부를 제한
- 상태 변경 요청의 `Origin` 또는 `Referer` 검증
- GET 요청으로 상태를 변경하지 않기
- 중요한 작업에 재인증이나 추가 확인 적용

`HttpOnly`는 자바스크립트의 쿠키 값 읽기를 막지만 브라우저의 자동 첨부까지 막지는 않으므로 단독으로 CSRF를 방어하지 못한다. CORS가 허용되지 않아도 `<form>`으로 만들 수 있는 단순 요청은 서버에 도달할 수 있으므로 CORS도 일반적인 CSRF 방어책으로 간주해서는 안 된다.

### SOP가 없다면 무엇이 가능한가?

공격자 페이지의 자바스크립트가 사용자의 인증 상태로 다른 사이트에 요청하고 그 응답까지 읽을 수 있다. 이메일·계좌 정보·구매 내역 등을 탈취하고, 응답에서 CSRF 토큰이나 일회성 값을 얻어 후속 요청을 정교하게 구성할 수 있다. 사내망, 공유기 관리 페이지, `localhost` 서비스도 공격 대상이 될 수 있다.

CSRF가 응답을 읽지 못한 채 인증된 요청을 실행하는 공격이라면, SOP가 없는 환경에서는 요청 실행과 응답 분석을 반복하며 사용자의 세션을 대화형으로 악용할 수 있다.

### 공격자가 origin을 조작할 수 있는가?

정상적인 브라우저에서는 origin을 현재 문서 URL의 `scheme + host + port`로 브라우저가 계산한다. 페이지 자바스크립트는 `Origin` 요청 헤더를 임의로 설정하거나 다른 사이트의 origin을 사칭할 수 없다.

공격자는 자신이 운영하는 도메인과 포트는 선택할 수 있다. 대상 사이트에 XSS 취약점이 있거나 서버·DNS 등을 장악했다면 대상 origin에서 코드가 실행될 수 있지만, 이는 origin 문자열을 단순 조작한 것이 아니라 보안 경계 내부의 실행 권한을 얻은 별도 취약점이다.

브라우저가 아닌 `curl` 등의 클라이언트는 `Origin`을 위조할 수 있으므로 서버가 이를 사용자 인증이나 권한 증명으로 사용해서는 안 된다. 외부 스크립트 파일은 일반적으로 파일을 내려준 CDN의 origin이 아니라 그 스크립트를 포함한 문서의 권한으로 실행된다는 점도 주의해야 한다.

### SOP를 브라우저가 집행하는 이유

SOP는 서버의 최종 방어선을 클라이언트에 맡기는 정책이라기보다, 사용자를 대신하는 브라우저가 서로 신뢰할 수 없는 웹 출처들을 격리하는 플랫폼 보안 정책이다.

브라우저는 현재 실행 중인 자바스크립트와 요청 대상의 origin, 쿠키, DOM, 창·iframe, 스토리지, 응답을 전달할 실행 문맥을 모두 알고 있다. 서버는 응답을 보낸 뒤 브라우저 안에서 어떤 다른 페이지의 코드가 그 DOM이나 기존 데이터를 읽는지 통제할 수 없다.

### 서버가 SOP를 처리하면 안 되는가?

서버가 `Origin`을 검사하는 것은 특히 CSRF 방어에 유효한 보조 수단이다. 브라우저가 생성한 요청에서는 페이지 자바스크립트가 이 헤더를 위조할 수 없기 때문이다. 하지만 서버 검사만으로 SOP 전체를 대체할 수 없다.

- 이미 열린 다른 출처 창이나 iframe의 DOM을 읽는 행위는 새 서버 요청 없이 브라우저 안에서 발생할 수 있음
- SOP는 HTTP 응답뿐 아니라 window, iframe DOM, 스토리지, 캔버스 등도 격리함
- 모든 요청에 `Origin`이 항상 존재하지는 않음
- 서버가 응답을 보낸 뒤 어느 실행 문맥에 공개할지는 브라우저만 결정할 수 있음
- 모든 서버가 완벽한 Origin 검사를 구현하도록 맡기면 누락된 서버가 곧 취약해짐

`curl`이 Origin만 위조하고 피해자의 쿠키나 토큰을 가지고 있지 않다면 피해자 계정의 데이터는 얻을 수 없다. 이 예시는 Origin 위조 자체가 계정 탈취라는 뜻이 아니라, Origin이 인증 수단이 될 수 없다는 뜻이다.

## 핵심 개념 정리

### Origin

```text
origin = scheme + host + port
```

예를 들어 `https://example.com:443`과 비교할 때 scheme, host, port가 모두 같아야 동일 origin이다.

### SOP

SOP는 브라우저가 서로 다른 origin의 실행 문맥과 데이터를 격리하는 기본 보안 정책이다. 교차 출처 요청 전송 전체를 차단하는 것이 아니라, 주로 다른 출처의 응답·DOM을 자바스크립트가 읽는 것을 제한한다.

### CORS

CORS는 서버가 특정 origin에 교차 출처 응답 읽기를 허용한다고 선언하고 브라우저가 이를 집행하는 메커니즘이다.

```text
요청:  Origin: https://frontend.example
응답:  Access-Control-Allow-Origin: https://frontend.example
```

메서드나 헤더가 단순 요청 범위를 벗어나면 브라우저가 실제 요청 전에 `OPTIONS` preflight를 보낼 수 있다. 서버는 `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` 등으로 허용 범위를 응답한다.

쿠키를 포함하는 credential 요청에서는 클라이언트의 credentials 설정과 서버의 `Access-Control-Allow-Credentials: true`가 필요하다. 이 경우 `Access-Control-Allow-Origin: *`를 사용할 수 없고 구체적인 origin을 반환해야 한다.

### SOP·CORS·CSRF의 차이

- SOP: 브라우저가 교차 출처의 응답·DOM 읽기를 기본적으로 제한
- CORS: 서버가 신뢰하는 origin에 SOP의 읽기 제한을 선택적으로 완화
- CSRF: 브라우저의 인증 정보 자동 첨부를 악용해 사용자가 의도하지 않은 상태 변경 요청 실행

## 모범 답안

> Origin은 URL의 scheme, host, port 조합이며 셋 중 하나라도 다르면 교차 출처입니다. SOP는 브라우저가 적용하는 보안 정책으로 다른 출처로 요청을 보내는 행위 전체를 금지하는 것이 아니라 주로 다른 출처의 응답이나 DOM을 자바스크립트가 읽는 것을 제한합니다.
>
> CORS는 서버가 특정 origin의 자바스크립트에 교차 출처 응답 읽기를 허용하는 메커니즘입니다. 브라우저가 요청의 `Origin` 헤더로 호출자의 출처를 알리고 서버가 `Access-Control-Allow-Origin`으로 허용 출처를 응답하면, 브라우저가 이를 검사해 응답을 자바스크립트에 공개합니다. 비단순 요청에서는 먼저 `OPTIONS` preflight를 보내 허용 메서드와 헤더를 확인합니다.
>
> SOP는 사용자의 브라우저 안에서 서로 신뢰할 수 없는 출처를 격리하며, 서버의 인증·인가나 CSRF 방어를 대신하지 않습니다. CSRF는 서버가 CSRF 토큰, SameSite 쿠키, Origin 검증 등으로 별도 방어해야 합니다.

## 복습 포인트

- Origin은 `scheme + host + port`이며 IP와 포트만이 아니다.
- SOP는 교차 출처 요청 전송 전체가 아니라 주로 응답·DOM 읽기를 제한한다.
- 브라우저가 `Origin`, 서버가 `Access-Control-Allow-Origin`을 보낸다.
- 비단순 요청의 `OPTIONS` preflight와 허용 메서드·헤더를 복습한다.
- CORS는 서버의 인증·인가나 일반적인 CSRF 방어를 대신하지 않는다.
- `HttpOnly`, `SameSite`, CSRF 토큰의 역할을 구분한다.
- SOP는 서버의 최종 방어선을 대신하는 것이 아니라 브라우저 내부 실행 문맥을 격리한다.
