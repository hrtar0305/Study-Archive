## Q1. HTTP의 정의·메시지 구조·stateless
- **내 답변 요약**: HTTP는 브라우저에서 URL의 리소스에 접근하고 클라이언트와 서버가 통신하기 위한 프로토콜이라고 설명했다. 요청과 응답이 헤더와 바디를 가진다고 답하고, stateless는 서버가 이전 요청을 자동으로 기억하지 않는 성질이며 쿠키로 로그인 상태를 보완할 수 있다고 설명했다.
- **평가**: HTTP는 클라이언트가 자원에 관한 요청을 보내고 서버가 응답하는 stateless 애플리케이션 계층 프로토콜이다. HTTP/1.1 요청은 request line·headers·body, 응답은 status line·headers·body로 구성된다. URL 경로는 request line에, 상태 코드는 status line에 있다. Stateless가 서버 측 상태 저장을 금지하는 것은 아니며, 쿠키의 세션 ID로 서버나 공용 저장소의 세션 상태를 찾을 수도 있다.

## Q2. HTTP 메서드·safe·idempotent
- **내 답변 요약**: GET은 조회, POST는 생성, PUT은 전체 교체, PATCH는 부분 수정, DELETE는 삭제라고 설명했다. GET·PUT·DELETE가 idempotent하고 POST는 일반적으로 그렇지 않으며, PUT을 재시도해도 최종 자원 상태가 같다고 답했다. safe의 의미를 제시하자 GET이 safe이고 safe이면 idempotent하지만 그 역은 성립하지 않는다고 설명했다.
- **평가**: 핵심 구분을 정확히 이해했다. Idempotent는 매 응답이 같다는 뜻이 아니라 한 번과 여러 번 수행했을 때 의도된 최종 서버 상태가 같다는 뜻이다. DELETE는 첫 요청과 이후 요청의 상태 코드가 달라질 수 있다. PUT·DELETE는 idempotent하지만 서버 상태를 바꾸므로 safe하지 않다. PATCH는 일반적으로 idempotency가 보장되지 않는다.

## Q3. HTTP 상태 코드와 redirect
- **내 답변 요약**: 2xx는 성공, 3xx는 redirect, 4xx는 client error, 5xx는 server error라고 답했다. 301·302·304와 401·403은 후보를 제시하자 대부분 정확히 연결했지만, 새 자원 생성 성공을 200으로 답했다. 304는 새 URL로 이동하는 것이 아니라 브라우저 캐시를 재사용하게 한다고 설명했다.
- **평가**: 새 자원 생성 성공은 201 Created다. 301은 영구 이동, 302는 임시 이동이다. 브라우저는 Location으로 자동 재요청할 수 있으며 이는 별도의 HTTP 요청이다. 301·302는 역사적으로 POST를 GET으로 바꿀 수 있으므로 메서드 보존에는 307·308을 사용한다. 304는 일반적인 URL redirect가 아니라 조건부 캐시 검증 응답이다. 401은 인증 정보가 없거나 유효하지 않은 경우, 403은 서버가 요청을 이해했지만 허용하지 않는 경우다.

## Q4. TLS 인증서와 CA 체인
- **내 답변 요약**: 서버는 신뢰할 수 있는 CA가 서명한 인증서를 제시하고 클라이언트가 이를 검증한다고 설명했다. 처음에는 루트 CA가 변경 불가능한 하드웨어에 있고 클라이언트가 CA에서 서버 인증서를 받아온다고 생각했다. 공개키·개인키의 서명 역할을 다시 확인한 뒤 루트 공개키로 중간 CA 인증서를 검증하고, 중간 CA 공개키로 서버 인증서를 검증하며 호스트명과 유효기간을 확인하는 흐름을 회복했다.
- **평가**: 루트 CA는 보통 OS·브라우저가 관리하는 소프트웨어 신뢰 저장소의 trust anchor다. 서버가 leaf 인증서와 필요한 중간 인증서를 보내며 루트 인증서는 보통 보내지 않는다. 클라이언트는 서명 체인, SAN의 호스트명, 유효기간, 키 용도 등을 확인한다. CA는 서버 개인키를 주는 것이 아니라 서버 공개키와 도메인의 관계를 인증서에 서명한다. 서버는 TLS CertificateVerify에서 핸드셰이크 내용에 서명해 대응하는 개인키 보유를 증명한다.

## Q5. 대칭키·비대칭키·ECDHE
- **내 답변 요약**: 대칭키는 서버와 클라이언트가 함께 사용하는 빠른 암호화 키이고, 안전한 키 합의를 위해 비대칭키를 사용한다고 설명했다. CA는 개인키로 서명하고 클라이언트는 공개키로 검증한다고 정확히 추론했다. ECDHE 질문에서는 RSA의 소인수분해 기반 키 전달과 임시 키 합의가 섞였지만, 세션마다 임시 개인값을 폐기하면 장기 개인키가 유출돼도 모든 과거 세션이 복호화되지 않는다는 목적을 설명했다.
- **평가**: 현대 TLS에서는 인증서의 장기 개인키가 서버 인증에 사용되고, ECDHE의 임시 공개값만 교환해 공유 비밀을 합의한다. 양쪽은 `aB=bA`인 같은 비밀을 계산하고 KDF로 방향별 대칭 세션 키를 파생한다. 실제 HTTP 데이터는 빠른 AEAD 대칭키 암호로 보호한다. ECDHE는 RSA의 소인수분해가 아니라 타원곡선 이산로그 문제에 기반하며 임시 개인값 폐기로 forward secrecy를 제공한다.

## Q6. HTTP/1.1·HTTP/2·HTTP/3
- **내 답변 요약**: HTTP/1.1의 HOL blocking을 HTTP/2가 multiplexing으로 줄이고, HTTP/3는 UDP 기반 QUIC을 사용한다고 설명했다. 처음에는 HTTP/2가 여러 경로로 전송한다고 답했지만, 하나의 TCP 연결이라는 조건 후 TCP 세그먼트 손실이 다른 스트림의 전달도 막는 이유를 설명했다. QUIC에서는 스트림 B가 A의 손실과 독립적으로 전달될 수 있다고 회복했다.
- **평가**: HTTP/1.1은 지속 연결을 제공하지만 pipelining의 응답 순서와 다중 TCP 연결 비용이 문제다. HTTP/2는 바이너리 프레이밍·HPACK·스트림 multiplexing으로 애플리케이션 계층 HOL을 줄이지만 하나의 TCP 바이트 스트림 때문에 손실 시 모든 스트림이 기다릴 수 있다. HTTP/3는 QUIC의 독립 스트림으로 전송 계층 HOL을 줄인다. 스트림 내부 순서 복구는 QUIC이 담당하며, 혼잡 제어와 대역폭은 공유될 수 있어 손실 영향이 완전히 사라지는 것은 아니다.

## Q7. HTTP 조건부 캐시 검증
- **내 답변 요약**: 304는 브라우저의 기존 캐시를 재사용하게 하고 200은 새 본문을 보낸다고 답했다. ETag·If-None-Match·Last-Modified·If-Modified-Since는 처음 기억하지 못했지만 힌트 후 요청 validator와 현재 자원을 비교해 304 또는 200을 결정하는 흐름을 정확히 설명했다.
- **평가**: 클라이언트가 If-None-Match 또는 If-Modified-Since를 보내므로 서버는 해당 버전의 캐시가 있다고 간접적으로 가정한다. 서버가 실제 캐시 본문을 확인하는 것은 아니다. 304를 받았는데 본문이 없다면 클라이언트는 조건부 헤더를 제거하고 일반 GET으로 재요청해야 한다. ETag는 자원 버전을 식별해 수정 시각의 해상도·메타데이터 한계보다 정밀할 수 있다.

## 후속 Q&A

### HTTP 한 문장 정의와 request-response
- HTTP는 클라이언트가 자원에 대한 요청을 보내고 서버가 그 결과를 응답하는 stateless 애플리케이션 계층 프로토콜이다.
- 통신 방식 전체는 request가 아니라 request-response exchange라고 표현한다.

### TLS 1.3 흐름
1. ClientHello에서 지원 버전·암호군·SNI·ALPN·ECDHE 공개값을 보낸다.
2. ServerHello에서 선택 결과와 서버 ECDHE 공개값을 보낸다.
3. 양쪽이 공유 비밀과 핸드셰이크 키를 파생한다.
4. 서버가 인증서 체인, CertificateVerify, Finished를 보낸다.
5. 클라이언트가 체인·호스트명·유효기간·개인키 보유 증명을 검증하고 Finished를 보낸다.
6. 파생한 대칭 application traffic key로 HTTP 데이터를 보호한다.

### TCP active·passive open과 종료
- Active open은 TCP 연결을 먼저 요청한 쪽이고 passive open은 listen하며 기다리는 쪽이다. 일반적으로 클라이언트와 서버 역할에 대응하지만, 클라이언트·서버는 애플리케이션 역할이고 TCP가 고정하는 명칭은 아니다.
- 먼저 FIN을 보내는 쪽은 active closer, 먼저 받는 쪽은 passive closer다. FIN은 한 방향의 송신 종료이므로 ACK와 상대 방향 FIN이 분리돼 일반적으로 4개 세그먼트가 된다.
- 양쪽이 동시에 FIN을 보내면 simultaneous close이며 양쪽 모두 CLOSING을 거쳐 TIME_WAIT에 들어갈 수 있다.
- 브라우저는 일반 HTTP에서 클라이언트이며 임의 TCP 포트를 listen하는 전통적인 서버로 동작하지 않는다. 프록시나 한 프로세스는 연결에 따라 클라이언트와 서버 역할을 모두 가질 수 있다.

### Expires·max-age·validator
- Expires는 절대 만료 시각이지만 캐시는 일반적으로 `Expires-Date`로 freshness lifetime을 계산한다.
- `Cache-Control: max-age=N`은 RFC 9111 기준으로 응답이 원본 서버에서 생성되거나 재검증된 뒤 N초가 지나면 stale하다는 뜻이다. 원본 서버에서 바로 받는 단순한 경우에는 수신 후 N초라고 근사할 수 있지만 중간 캐시를 거쳤다면 Age 등 이미 경과한 시간을 제외한다.
- fresh 여부는 `freshness_lifetime > current_age`로 판단한다. Age는 원본에서 생성·재검증된 이후의 추정 경과 시간이다.
- max-age가 남아 있으면 서버 변경을 자동으로 알 수 없으므로 이전 응답을 사용할 수 있다. 변경이 잦은 자원은 짧은 max-age와 validator, 항상 검증할 자원은 no-cache, 저장 금지는 no-store를 사용한다.
- 정적 자원은 콘텐츠 해시를 파일명에 넣고 긴 max-age와 immutable을 사용하는 cache busting이 일반적이다.
- no-cache는 저장 금지가 아니라 사용 전 재검증을 뜻한다.

참고: [RFC 9111 — HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)

## 음성 답변의 사고 흐름·구성 평가

### 잘한 점
- safe와 idempotent의 관계를 정의에서 출발해 논리적으로 설명했다.
- 공개키·개인키의 서명 역할을 복원한 뒤 인증서 체인의 검증 순서를 스스로 연결했다.
- ETag 조건부 요청은 힌트의 요소들을 올바른 흐름으로 조립했다.
- TCP HOL과 QUIC 독립 스트림도 구체적인 손실 상황이 주어지자 원리를 회복했다.

### 개선할 점
- "다시 이야기하겠습니다"로 답변 전체를 여러 번 재시작해 결론이 늦게 나오는 경우가 많았다.
- RSA 기반 키 전달과 ECDHE 키 합의처럼 서로 다른 모델을 하나의 설명에 섞는 경향이 있었다.
- 여러 후보를 검토한 뒤 정답을 찾았어도 이전 표현이 최종 문장에 남아 모순처럼 들리는 경우가 있었다.
- 답변을 `결론 → 이유 → 구체적인 과정` 순서로 고정하고, 전체를 다시 시작하기보다 틀린 문장만 짧게 정정하는 연습이 필요하다.
- 명백한 받아쓰기 변환 오류는 지식 오류로 평가하지 않았으며 발화 속도·억양·발음은 평가 대상이 아니다.

## 모범답안 요점

HTTP는 stateless한 애플리케이션 계층의 request-response 프로토콜이다. 메서드의 safe·idempotent 성질과 상태 코드에 따라 요청 처리 의미가 정해지고, 쿠키·세션·토큰으로 필요한 상태를 보완한다.

HTTPS는 HTTP를 TLS로 보호해 기밀성·무결성·서버 인증을 제공한다. 클라이언트는 루트 CA부터 서버 인증서까지 서명 체인과 호스트명·유효기간을 검증한다. 서버는 인증서 개인키로 핸드셰이크에 서명하고, 양쪽은 ECDHE 공유 비밀에서 파생한 대칭키로 실제 데이터를 암호화한다.

HTTP/2는 하나의 TCP 연결에서 스트림을 다중화하지만 TCP HOL이 남는다. HTTP/3는 QUIC의 독립 스트림으로 이를 줄인다. HTTP 캐시는 freshness 동안 본문을 재사용하고, 만료 후 ETag나 Last-Modified로 조건부 요청해 변경이 없으면 304와 기존 본문을 결합한다.
