## 개념 1: 해시 테이블

### Q1. 해시 테이블이란? 평균 O(1) 탐색이 가능한 원리는?
- **내 답변 요약**: 해시함수 + array로 키 탐색을 평균 O(1)에 수행하는 자료구조. key를 해시함수에 넣고 테이블 크기로 모듈러를 취해 deterministic한 index로 변환, array는 index 접근이 O(1)이므로 버킷을 빠르게 찾음.
- **평가**: 정확성·구조화 우수. 핵심 사슬(해시함수→모듈러→O(1) 인덱스 접근)을 명확히 설명.
- **모범답안**: 키-값 쌍 저장 자료구조. 해시함수가 키를 정수로 변환, 테이블 크기로 모듈러 → 버킷 인덱스 결정. 배열 인덱스 접근 O(1) + 충돌이 적다는 가정(균등 분포) 하에 평균 O(1).

### Q2. 충돌이란? 해결책 종류는?
- **내 답변 요약**: 비둘기집 원리·확률에 의해 서로 다른 키가 같은 버킷을 가리키는 현상 = hash collision. 해결책: open addressing, separate chaining.
- **평가**: 비둘기집 원리 연결 좋음. 정확.

### Q3. 두 방식 동작 + trade-off
- **내 답변 요약**: chaining = 버킷을 링크드리스트로 구현, 충돌 시 체인에 추가. 구현 간단·무제한 추가 가능하나 최악 체인 길이만큼 추가시간 + 메모리 locality 희생. open addressing = 충돌 시 추가 probing으로 빈 버킷 할당. 탐색 비용 추가되나 array 그대로 써서 캐시 locality 좋음.
- **평가**: 동작·locality trade-off는 우수. **누락**: ① probing 종류(linear/quadratic/double hashing)와 clustering 현상, ② load factor 민감도 차이(open addressing은 α→1에서 급격 저하, chaining은 우아하게 저하·α>1도 가능).
- **모범답안 보강**: linear probing은 primary clustering 유발, quadratic·double hashing이 완화. chaining은 삭제 단순(포인터 재연결)·부하율 제약 느슨하나 포인터 추적으로 캐시 비효율.

### Q4. open addressing 삭제 문제 + 해결
- **내 답변 요약**: 단순 삭제하면, 그 칸을 지나 자기 버킷으로 probing해야 할 다른 키가 빈 칸에서 탐색을 멈춰 자기 버킷을 못 찾음. → tombstone 표시로 처리.
- **평가**: 완벽. probing이 빈 칸에서 종료되는 성질과 tombstone 해결 모두 정확.

### Q5. load factor / resizing / amortized O(1)
- **내 답변 요약**: 원소 많아지면 충돌 확률↑(=로드팩터). 사용 버킷/전체 버킷, 보통 0.7 초과 시 조치. 리사이징(새 테이블 할당 후 이전) 비용 O(N), 다음 리사이징까지 O(1)이므로 amortized O(1).
- **평가**: 흐름 정확. **용어 부정확**: load factor는 "충돌 확률이 높아지는 현상"이 아니라 **비율 자체**(α = 사용 버킷 수 / 전체 버킷 수). 임계치·amortized 결론은 정확.

### Q6 & Q7. 2배 vs 고정증가 amortized 정량 분석
- **내 답변 요약**: 리사이징 비용은 새 테이블 크기와 무관하게 기존 원소 수만큼 발생. 고정증가(+c)면 같은 비용이 더 자주 발생해 상환 안 됨. N 삽입 총비용 → amortized O(N).
- **평가**: 천장 도달. 고정증가 시 복사 총비용 c+2c+…≈N²/2c=O(N²) → 1회당 amortized O(N) 정확. 2배 증가 시 등비급수로 O(N) 수렴 → amortized O(1) 대비까지 이해.

### 체크포인트 추가 Q&A (사용자 질문)
1. **"빈 칸을 건너뛰게 하면 tombstone 불필요한 것 아닌가?"** → 빈 칸은 탐색 종료 신호("키 없음 확정"). 건너뛰면 unsuccessful search가 O(n)으로 퇴화. tombstone은 "삭제된 칸만 통과 + 진짜 빈 칸은 종료 유지"로 절충. linear probing 한정 backward-shift deletion(Robin Hood)으로 tombstone 없이도 가능.
2. **"tombstone은 따로 정리 안 하나?"** → 즉시 정리 안 함. 삽입 시 재활용 + rehash(전체 재구축) 때 일괄 제거. tombstone 비율 임계 초과 시 같은 크기로 rehash 트리거하기도.
3. **"amortized 비용은 탐색? 삽입?"** → 삽입(상태 변경 연산). 탐색은 rehash 유발 안 하므로 해당 없음. 삭제로 인한 shrink 포함 시 확장·축소 임계치 간격 둬야 thrashing 방지.
4. **"점진적 rehashing 맞나?"** → 맞음(de-amortization). Redis dict(ht[0]/ht[1] + rehashidx, 연산마다 버킷 몇 개씩 이전, 조회는 두 테이블 모두 확인). DB 쪽은 linear hashing/extendible hashing(버킷 하나씩 split). Java HashMap은 블로킹 resize.
5. **"average O(1)은 개념상인가? average vs amortized 차이?"** → average O(1)은 α를 상수로 묶고 균등 해싱 가정 시에만 성립. chaining O(1+α), open addressing 실패탐색 1/(1−α)(α→1 발산). worst-case는 O(n). **average**(단일 연산, 확률 의존) vs **amortized**(시퀀스 전체, 결정적 보장)는 다른 개념. 삽입은 amortized(리사이징)+average(해싱), 탐색은 average O(1).

### 약점·복습포인트 (해시 테이블)
- probing 종류(linear/quadratic/double hashing)와 primary/secondary clustering 현상 — 첫 답변에서 누락
- chaining vs open addressing의 **load factor 민감도 차이** — 정량(α 함수)으로 설명 보강 필요
- load factor의 **정의**를 "충돌 확률"로 부정확하게 표현 (정확히는 비율 α = n/m)
