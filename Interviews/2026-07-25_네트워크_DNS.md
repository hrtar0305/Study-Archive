## Q1. DNS의 정의와 필요성
- **내 답변 요약**: DNS는 Domain Name System의 약자로, 사람이 기억하기 쉬운 문자열 이름을 실제 서버의 IP 주소에 매칭해 주는 서비스라고 설명했다.
- **평가**: 핵심 목적은 정확했다. DNS가 도메인 이름과 여러 종류의 레코드를 관리하는 계층적·분산형 데이터베이스라는 점을 보완하면 더 완전하다.

## Q2. DNS 조회 과정
- **내 답변 요약**: 브라우저 캐시에 값이 없으면 OS 캐시를 확인하고, 이후 중간 DNS 시스템이 루트·TLD·권한 DNS 서버를 거쳐 최종 IP 주소를 얻는다고 설명했다.
- **평가**: 전체 계층 흐름은 알고 있었다. 일반적으로 PC가 루트부터 직접 조회하지 않고 재귀 리졸버가 대신 수행한다. 루트 서버는 12개가 아니라 A~M의 13개 논리적 식별자가 있으며 Anycast로 배치된 실제 인스턴스는 훨씬 많다.

## Q3. 스텁·재귀 리졸버와 질의 방식
- **내 답변 요약**: 처음에는 스텁 리졸버와 재귀 리졸버의 역할을 반대로 연결했다. 힌트 후 사용자 PC 내부에서 최소 기능으로 요청을 전달하는 것이 스텁 리졸버이고, 통신사 DNS나 공용 DNS에서 최종 답을 대신 구하는 것이 재귀 리졸버임을 회복했다.
- **평가**: 스텁 리졸버는 설정된 재귀 리졸버에 일반적으로 재귀 질의를 보낸다. 재귀 리졸버는 캐시가 없으면 루트·TLD·권한 서버에 반복 질의를 보내며 referral을 따라간다.

## Q4. DNS 캐시와 TTL
- **내 답변 요약**: TTL은 캐시가 유효한 기간이고, TTL 동안에는 이후 조회를 생략하고 캐시 값을 사용한다고 설명했다. 첫 답변에서 긴 TTL과 짧은 TTL의 효과를 뒤섞었지만, 24시간과 5초의 구체적인 조건이 주어지자 변경 반영 속도·조회 부하·응답 지연의 trade-off를 정확히 정리했다.
- **평가**: 긴 TTL은 캐시 적중률을 높여 부하와 지연을 줄이지만 변경 반영이 느리다. 짧은 TTL은 변경을 빨리 반영하지만 조회 부하와 지연이 커진다. IP 변경 후 일부 사용자에게 이전 주소가 남는 것은 각 캐시의 남은 TTL이 다르기 때문이다.

## Q5. DNS의 UDP·TCP 사용
- **내 답변 요약**: DNS는 일반적으로 UDP를 사용하고, 응답이 커서 잘리거나 대량 레코드를 복사하는 경우 TCP를 사용할 수 있다고 설명했다. 표준 포트는 기억하지 못하고 8080으로 추측했다. TC 비트가 설정되면 TCP로 다시 요청해야 함을 추론했다.
- **평가**: DNS의 표준 포트는 UDP·TCP 모두 53번이다. UDP 응답의 TC(Truncated) 비트가 설정되면 TCP로 재질의할 수 있다. AXFR·IXFR 같은 zone transfer는 크고 신뢰성 있는 전송이 필요하므로 TCP를 사용한다.

## Q6. DNS 레코드 타입
- **내 답변 요약**: 처음에는 레코드 타입을 기억하지 못했지만 역할이 제시되자 A는 IPv4, AAAA는 IPv6, CNAME은 다른 도메인을 가리키는 별칭, MX는 메일 서버, NS는 권한 DNS 서버로 연결했다. CNAME을 받으면 대상 도메인을 다시 조회해야 한다고 설명했다.
- **평가**: 역할 매칭과 CNAME의 추가 조회 흐름을 회복했다. CNAME 대상의 A 또는 AAAA 레코드를 조회해 최종 IP 주소를 얻는다.

## Q7. 캐시 포이즈닝·DoH·DNSSEC
- **내 답변 요약**: 공격자가 정상 응답보다 악성 IP를 담은 위조 응답을 먼저 보내 재귀 리졸버가 TTL 동안 캐시하게 만드는 시나리오를 추론했다. 트랜잭션 ID와 UDP 출발지 포트의 역할은 답하지 못했다. DoH는 HTTPS를 이용해 통신 경로를 암호화하고, DNSSEC는 DNS 레코드의 출처와 무결성을 검증하는 방식이라고 구분했다.
- **평가**: 공격자가 반드시 중간자일 필요는 없다. 경로 밖의 공격자도 트랜잭션 ID와 UDP 출발지 포트를 추측해 질의와 일치하는 위조 응답을 정상 응답보다 먼저 도착시키려 할 수 있다. DoH는 클라이언트와 DoH 리졸버 사이를 암호화하지만 데이터의 진위를 보장하지 않는다. DNSSEC는 RRSIG·DNSKEY·DS와 루트부터 이어지는 신뢰 체계로 출처와 무결성을 검증하지만 기밀성을 제공하지 않는다.

## 음성 답변의 사고 흐름·구성 평가

### 잘한 점
- 기억이 불완전할 때 알고 있는 전체 구조와 각 구성요소의 역할을 이용해 답을 추론했다.
- TTL과 CNAME 문제에서는 구체적인 조건이나 역할이 주어지자 빠르게 정답을 회복했다.
- DoH는 약어를 풀고 HTTPS 기반 통신이라는 기능까지 곧바로 연결했다.
- 답이 잘못 전개됐다고 느낄 때 처음부터 다시 설명하거나 명시적으로 정정하려 했다.

### 개선할 점
- 스텁·재귀 리졸버 답변처럼 여러 후보를 소리 내어 바꾸면서 최종 문장에도 모순되는 표현이 남는 경우가 있었다.
- "정확히 기억나지 않는다"는 전제가 반복되면서 결론이 늦게 나오는 경향이 있었다. 먼저 현재 판단을 한 문장으로 제시하고 근거를 붙이는 편이 명확하다.
- 전체 답변을 처음부터 다시 시작하기보다 "정정하겠습니다. PC 내부가 스텁 리졸버입니다."처럼 정정 범위를 좁히면 전달력이 좋아진다.
- `재귀 질의`가 다른 말로 변환되는 등 명백한 받아쓰기 오류는 지식 오류로 평가하지 않았다.

## 모범답안 요점

DNS는 도메인 이름을 IP 주소와 각종 레코드에 연결하는 계층적·분산형 이름 시스템이다. 애플리케이션은 일반적으로 OS의 스텁 리졸버를 통해 설정된 재귀 리졸버에 재귀 질의를 보낸다. 캐시가 없다면 재귀 리졸버가 루트·TLD·권한 DNS 서버에 반복 질의를 보내 최종 레코드를 얻고 TTL 동안 캐시한다.

DNS는 일반적으로 UDP 53번을 사용한다. 응답의 TC 비트가 설정되면 TCP 53번으로 다시 조회할 수 있으며 zone transfer도 TCP를 사용한다. A는 IPv4, AAAA는 IPv6, CNAME은 별칭, MX는 메일 서버, NS는 권한 DNS 서버를 나타낸다.

캐시 포이즈닝 공격자는 질의와 일치하는 트랜잭션 ID와 UDP 출발지 포트 등을 추측한 위조 응답을 정상 응답보다 먼저 도착시키려 한다. DoH는 통신 경로를 암호화하고 DNSSEC는 전자서명과 신뢰 체계를 통해 레코드의 출처와 무결성을 검증하므로 둘은 서로 다른 문제를 해결한다.
