## Q1. 라우팅과 포워딩의 차이

- **질문**: 네트워크에서 라우팅과 포워딩은 각각 무엇이며 두 동작은 어떻게 다른가?
- **내 답변 요약**: 라우팅은 출발지에서 목적지까지 경로를 찾는 과정이고, 포워딩은 비슷하지만 고정된 규칙을 통해 전달하는 차이가 있다고 답했다.
- **평가**: 라우팅이 경로를 찾는 작업이라는 핵심은 맞았다. 포워딩은 새로운 경로를 찾는 작업이 아니라 이미 계산·설치된 전달 정보를 이용해 개별 패킷의 다음 홉과 출력 인터페이스를 정하는 작업이다. 포워딩 테이블은 라우팅 변화에 따라 갱신되므로 고정된 규칙이라는 표현은 부정확하다.
- **모범답안**: 라우팅은 제어 평면에서 정적 설정이나 라우팅 프로토콜을 통해 목적지 prefix의 후보 경로를 학습하고 최적 경로를 선택하는 작업이다. 포워딩은 데이터 평면에서 패킷마다 목적지 IP로 FIB를 조회해 다음 홉과 출력 인터페이스로 실제 전달하는 작업이다.

## Q2. 제어 평면·데이터 평면과 테이블

- **질문**: 라우팅과 포워딩은 각각 어느 평면에서 수행되며 어떤 테이블을 만들거나 조회하는가?
- **내 답변 요약**: 제어 평면과 데이터 평면은 잘 모르겠다고 답했다. 힌트 후 경로 계산은 라우팅이고 라우팅 테이블을 기반으로 하며, 포워딩은 포워딩 테이블을 기반으로 할 것이라고 추론했다.
- **평가**: 라우팅과 포워딩에 서로 다른 테이블이 연결된다는 점은 추론했다. 그러나 제어·데이터 평면을 대응시키지 못했고, 라우팅 테이블을 라우팅의 입력으로만 이해해 경로 학습·선택의 결과라는 점이 불명확했다. 힌트 이후에도 기초 구분이 완성되지 않아 정식 면접 질문은 여기서 마무리했다.
- **모범답안**:
  - 제어 평면: 라우팅 프로토콜 실행, 후보 경로 학습·비교, RIB 관리, 선택 결과를 FIB에 설치
  - 데이터 평면: 실제 패킷마다 FIB를 Longest Prefix Match로 조회해 다음 홉과 출력 인터페이스로 전달

```text
제어 평면: 경로 학습·계산 → RIB 구성 → 최적 경로를 FIB에 반영
데이터 평면: 패킷 수신 → FIB 조회 → 다음 홉·출력 인터페이스로 전달
```

## 후속 학습

### 라우팅과 포워딩은 어디서 수행되는가

동적 라우팅을 사용하는 중간 라우터들은 모두 라우팅 프로토콜에 참여할 수 있다. 각 라우터는 자신의 관점에서 목적지 prefix에 대한 다음 홉을 미리 계산·선택하고 FIB에 설치한다. 패킷이 실제로 도착했을 때는 전체 종단 간 경로를 다시 계산하지 않고 자신의 FIB에서 다음 홉을 조회한다.

```text
A → R1 → R2 → R3 → B

미리 수행되는 라우팅:
R1: B의 네트워크 → R2
R2: B의 네트워크 → R3
R3: B의 네트워크 → 직접 연결

패킷마다 수행되는 포워딩:
R1 FIB 조회 → R2로 전달
R2 FIB 조회 → R3로 전달
R3 FIB 조회 → B로 전달
```

각 라우터의 홉별 선택이 연결되어 종단 간 경로가 형성된다. 동적 라우팅의 `동적`은 패킷마다 계산한다는 뜻이 아니라 토폴로지와 정책 변화에 자동으로 반응한다는 뜻이다.

### 라우팅이 실행·재계산되는 시점

라우팅 프로세스는 계속 실행되지만 실제 경로 재계산과 테이블 갱신은 주로 다음 이벤트에서 발생한다.

- 라우터 부팅과 라우팅 인접 관계 형성
- 인터페이스 up·down
- 이웃 라우터 연결 생성·종료
- 새로운 prefix 광고 또는 기존 prefix 철회
- 링크 metric이나 라우팅 정책 변경
- 다른 라우터에서 변경된 경로 정보 수신
- 경로·인접 관계 유지 타이머 만료

직접 연결된 장애는 물리 인터페이스 상태, Hello·Dead Timer, BFD 등으로 감지한다. 멀리 있는 장애는 해당 링크에 인접한 라우터가 먼저 감지한 뒤 라우팅 프로토콜 메시지로 전파한다.

OSPF에서는 링크 변화가 LSA로 flooding되고, 각 라우터가 LSDB를 갱신한 뒤 SPF를 다시 계산한다. BGP에서는 TCP 세션 종료, Keepalive·Hold Timer, UPDATE·withdraw 등을 통해 경로 변화를 감지하고 전파한다.

```text
토폴로지·경로 변경
→ 인접 라우터가 감지
→ 라우팅 메시지로 변경 전파
→ 각 라우터가 경로 재선택
→ RIB·FIB 갱신
→ 이후 패킷은 새 FIB로 포워딩
```

### 제어 평면과 데이터 평면

두 평면은 우선 역할에 따른 논리적·아키텍처적 구분이다.

- 제어 평면: 어디로 보낼지 결정하고 전달 상태를 준비
- 데이터 평면: 준비된 상태를 이용해 실제 패킷 전달

일반적인 하드웨어 라우터에서는 제어 평면을 CPU·라우팅 프로세서가, 데이터 평면을 라인 카드·ASIC·TCAM이 담당할 수 있다. 소프트웨어 라우터에서는 같은 컴퓨터 안의 서로 다른 프로세스와 커널 기능으로 구현될 수 있다. SDN에서는 외부 컨트롤러가 제어 평면을 맡고 스위치가 데이터 평면만 수행하는 식으로 물리적 분리가 더 강해질 수 있다.

제어 평면이 잠시 중단되어도 기존 FIB가 남아 있으면 포워딩이 계속될 수 있고, 반대로 라우팅 프로토콜은 정상이어도 데이터 평면의 ASIC·인터페이스 장애로 실제 패킷이 전달되지 않을 수 있다.

### RIB와 FIB

RIB와 FIB에는 `목적지 prefix → 다음 홉`이라는 핵심 정보가 겹치지만 용도와 포함 범위가 다르다.

#### RIB

RIB는 제어 평면의 경로 선택 데이터베이스다. 정적·연결·OSPF·BGP 등에서 학습한 후보 경로와 선택에 필요한 정보를 관리한다.

- 경로 출처
- next hop
- metric·administrative distance
- OSPF cost
- BGP LOCAL_PREF·AS_PATH·MED
- 최적 경로와 백업 후보

#### FIB

FIB는 RIB에서 선택된 경로를 실제 포워딩에 적합한 형태로 가공한 데이터 구조다.

- 실제 설치된 최적 경로 또는 ECMP 경로
- 해결된 다음 홉
- 출력 인터페이스
- 플랫폼에 따라 adjacency·패킷 재작성 정보 참조

```text
RIB:
203.0.113.0/24
├─ 경로 A: 10.0.0.2, cost 10  ← 선택
└─ 경로 B: 10.0.1.2, cost 30

FIB:
203.0.113.0/24 → next hop 10.0.0.2 → eth0
```

패킷이 도착할 때 OSPF cost나 BGP 속성을 다시 비교하지 않는다. FIB에 이미 설치된 결과를 빠르게 조회한다. 다음 홉 IP의 MAC 주소는 별도의 ARP·이웃 테이블에 저장되거나 FIB가 adjacency 정보를 참조한다.

### OSPF와 BGP 기초

- OSPF: AS 내부에서 사용하는 링크 상태 IGP. LSA를 공유하고 Dijkstra 기반 SPF로 비용이 낮은 경로를 계산한다.
- BGP: 주로 AS 사이에서 prefix 도달 가능성을 교환하는 경로 벡터 프로토콜. 단순 최단거리보다 LOCAL_PREF·AS_PATH·MED 등 경로 속성과 운영 정책을 중시한다.
- BGP는 AS_PATH에 자신의 AS가 포함된 경로를 거부해 AS 수준의 루프를 방지한다.

## 핵심 정리

```text
라우팅:
제어 평면에서 경로를 학습·비교·선택
→ RIB 관리
→ 선택 결과를 FIB에 설치

포워딩:
데이터 평면에서 패킷마다 FIB 조회
→ 다음 홉·출력 인터페이스 결정
→ 실제 전달
```

라우팅과 포워딩은 경로의 계산·유지와 실행이라는 밀접한 관계지만 서로 다른 시점과 평면에서 수행되는 별개 기능이다. 라우팅은 토폴로지나 정책이 변할 때 반응하고, 포워딩은 모든 패킷에 대해 기존 FIB를 사용한다.

RIB는 후보 경로와 경로 선택용 메타데이터를 관리하고, FIB는 선택 결과를 실제 전달에 최적화한 실행용 테이블이다.
